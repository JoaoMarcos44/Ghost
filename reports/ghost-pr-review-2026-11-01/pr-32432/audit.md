# PR #32432 — independent correctness and trust-boundary audit

**Audited head:** [`af654561e2f883f086fd694abede433abfffff6b`](https://github.com/TryGhost/Ghost/commit/af654561e2f883f086fd694abede433abfffff6b). **PR base in the supplied API snapshot:** [`80b4c5d8f8a7cb90a93caa072140c54d4cb5b69b`](https://github.com/TryGhost/Ghost/commit/80b4c5d8f8a7cb90a93caa072140c54d4cb5b69b). The merge base and head's parent are `5d4430c8c157990adbd69400f4cee9795037fbbb`; the seven newer base commits did not change `koenig/`. The worktree was clean at the start of the audit.

## Definite finding: imported formatted words can join in newsletter output (P2)

For an HTML toggle whose body contains `<p><strong>Hello</strong> <em>world</em></p>`, the new [parser preserves the element markup and the intervening space](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-default-nodes/src/nodes/toggle/toggle-parser.ts#L14). The normal web renderer then displays `Hello world`. However, the [email toggle template](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-default-nodes/src/nodes/toggle/toggle-renderer.ts#L31) interpolates the content into the `html` tag, whose existing [`_oneline` implementation removes whitespace between tags](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-default-nodes/src/utils/tagged-template-fns.ts#L4). The email contains `<strong>Hello</strong><em>world</em>`, so its text reads **`Helloworld`**. The same problem affects heading markup, e.g. `<strong>Heading</strong> <em>words</em>` becomes `Headingwords`.

This is reachable through the production email path: Ghost's email renderer [passes the saved Lexical document to the renderer with `target: 'email'`](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/ghost/core/server/services/email-service/email-renderer.js#L573). The independent sandbox test used the actual `htmlToLexical` and `LexicalHTMLRenderer` source at the audited head, not only an isolated replacement function. It observed:

| Revision | Imported body stored | Web text | Email text | Email heading text |
| --- | --- | --- | --- | --- |
| Base `80b4c5d` | `Hello world` | `Hello world` | `Hello world` | `Heading words` |
| Head `af65456` | `<p><strong>Hello</strong> <em>world</em></p>` | `Hello world` | `Helloworld` | `Headingwords` |

The whitespace-removal helper and its effect on a directly supplied rich Lexical toggle predate this PR. The regression shown here is narrower: for the *same HTML import*, the base loses formatting but keeps the visible words separated in email, while this PR preserves the formatting and newly exposes the existing email bug. This does not imply that all pre-existing toggle newsletter rendering was correct. A reasonable fix is to preserve content whitespace when constructing the toggle email template, with tests for adjacent inline elements in both heading and body and an HTML-import-to-email integration test. Avoid changing the shared whitespace helper globally without considering its other callers. The PR's [round-trip test](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-html-to-lexical/test/html-to-lexical.test.ts#L677) calls `exportDOM` with the default web target; its existing [email test](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-default-nodes/test/nodes/toggle.test.ts#L187) uses only plain text.

## Confirmed boundaries and compatibility limits

- **The main web fix works for the demonstrated supported content.** The independent test confirmed preservation of emphasis, a link destination and two paragraphs through the real converter and web renderer. Escaped markup remains text at head; on the base, text extraction followed by HTML interpolation could turn that escaped markup into elements. A separate test exercised the actual nested-editor HTML conversion helper, node lists and `cleanBasicHtml`, and confirmed that the supported emphasis, link and paragraphs survive those operations. It did not run a browser or a full Admin save.
- **HTML input is not inherently trusted merely because the callback is typed.** The production [posts](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/ghost/core/server/api/endpoints/utils/serializers/input/posts.js#L223) and [pages](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/ghost/core/server/api/endpoints/utils/serializers/input/pages.js#L179) `source=html` paths pass submitted HTML into the converter; [HTML-only legacy imports do likewise](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/ghost/core/server/data/importer/importers/data/posts-importer.js#L308). In contrast, the separate content-import path [can clean HTML before conversion](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/ghost/core/server/services/content-import/import/post-data.ts#L128); this audit did not establish what that cleaner permits.
- **Active attributes now survive this particular toggle conversion.** In the sandbox, `<img src="x" onerror="auditMarker()">` inside `.kg-toggle-content` retained `onerror` in the head's converted and rendered HTML, whereas the base's `textContent` discarded the image element. The test did not execute the handler. The same test showed that an [explicit raw HTML card](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-default-nodes/src/nodes/html/html-parser.ts#L5) already retained that attribute on both revisions. Thus this establishes a changed data flow, **not** a proven new privilege escalation or exploitable XSS: the allowed actor, source, downstream sanitization assumptions and any cross-trust-boundary workflow require separate verification. The server-side [toggle renderer interpolates both fields as HTML](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/kg-default-nodes/src/nodes/toggle/toggle-renderer.ts#L18); opening the editor uses nested Lexical conversion and its own [export normalization](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/koenig-lexical/src/nodes/ToggleNode.tsx#L61), so those paths should not be conflated.
- **Unsupported markup has a durability limit.** The head's parser preserves an image nested inside a toggle and the web renderer can output it, but the reproduced nested-editor conversion with the actual [`BASIC_NODES`](https://github.com/TryGhost/Ghost/blob/af654561e2f883f086fd694abede433abfffff6b/koenig/koenig-lexical/src/nodes/BasicNodes.ts#L5) drops the image when serializing that content. This is a helper-level observation rather than a browser-tested save finding; the base discarded the image during the original HTML import, so it is not evidence of a new loss of previously supported content. It does mean that “preserve rich content” should be understood in terms of the editor's supported content, not arbitrary HTML durability.
- **Malformed and email-target input:** a `.kg-toggle-card` missing both expected field elements converts to an empty toggle on both revisions. The email renderer emits a table, and importing that table produces an HTML card on both revisions, not an editable toggle. These behaviors predate the PR; no requirement that email-target HTML round-trip into an editable toggle was established.

## Documentation and reviewer assessment

The PR description correctly explains the loss of formatting and discloses that the broad check was not completed. Its round-trip claims and the linked [visual explanation](https://github.com/JoaoMarcos44/Ghost/blob/e2433b625dc9f4776ecbf3dec55e7ca4c2f7849f/reports/ghost-prs-2026-10-31/toggle/infographic_report.md) would be clearer if they distinguished the verified **web** path from the email target and stated that arbitrary markup is not guaranteed to survive editor reserialization. The converter and node READMEs do not spell out an HTML trust/sanitization contract; document that boundary if maintainers intend consumers to rely on one. Public HEAD requests to the pinned evidence Markdown, infographic report and PNG URLs returned HTTP 200 during this audit.

The supplied snapshot contains **zero formal reviews, zero inline comments, and one CodeRabbit conversation comment**. The [automated summary](https://github.com/TryGhost/Ghost/pull/32432#issuecomment-6550183270) says it found no actionable comments, describes the formatting fix accurately, and rates merge risk minimal. Its type-safe-boundary statement is fair insofar as the conversion callback is an internal, typed TypeScript API; it does not establish the provenance or safety of the HTML entering through upstream routes. The two ast-grep XSS warnings cited in that comment target `rendered = element.outerHTML` in tests: those statements **read** a property into a string, rather than assign untrusted input to `outerHTML`, so the specific warnings do not establish a vulnerability. Nevertheless, the missing email coverage and real input/output behavior above make the “minimal” assessment incomplete.

## Validation and limitations

The deliberate reproducible evidence files are [audit-toggle.test.ts](audit-toggle.test.ts), [audit-editor.test.ts](audit-editor.test.ts), and [run-audit.py](run-audit.py). On this Windows checkout, run:

```powershell
python -X utf8 C:/Users/Nitro/Ghost/reports/ghost-pr-review-2026-11-01/pr-32432/run-audit.py
```

The runner copied source into an isolated temporary directory, reused the already-installed dependencies through junctions without intending to modify them, replaced only the copied parser with the exact base version for the base phase, and ran the same source-level suite at base and head with Node 22.23.4, Vitest 4.1.12, one worker and a 2048 MB Node heap limit. The Koenig source other than the changed parser is the same between these revisions. **Both phases passed 8/8 tests (exit 0);** these assertions deliberately record the observed email defect rather than assert that email output is correct. Both temporary sandboxes were removed immediately; a process check found no Node process from either sandbox. The earlier six-case version also passed 6/6 per revision before the nested-editor cases were added.

This was not a full repository check, browser E2E, HTTP API/database integration test, actual email delivery, or test of third-party sanitization. The PR's own reported 16/16 and 37/37 focused tests and commit-hook results were not independently rerun here. No product files were edited.
