# PR #32434 audit

Reviewed head [`779635571ba48999068a61ae56ec1ae98678509e`](https://github.com/TryGhost/Ghost/commit/779635571ba48999068a61ae56ec1ae98678509e), whose parent and PR merge base are [`5d4430c8c157990adbd69400f4cee9795037fbbb`](https://github.com/TryGhost/Ghost/commit/5d4430c8c157990adbd69400f4cee9795037fbbb). The captured target-branch head was `80b4c5d8f8a7cb90a93caa072140c54d4cb5b69b`. This is a source audit and focused isolated probe, not a completed browser, MySQL, or HTTP review.

The fix addresses the reported selection bug: the new action reads matching member IDs once and deletes selected label relations within one transaction. The supplied SQLite probe confirms the central behavior and rollback. There is a confirmed, narrow SQLite parameter-limit regression for large selections; there is also a confirmed response/type mismatch exposed by the new type, but the serializer defect predates this PR. Browser acceptance and MySQL/HTTP validation remain necessary before treating the change as fully validated.

## Confirmed findings

### 1. Large multi-label requests can exceed SQLite's SQL-variable limit

The new [repository branch](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/services/members/members-api/repositories/member-repository.js#L1262) passes *all* selected member IDs and requested label IDs to one [relation lookup](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/models/member.js#L700). Both `whereIn` lists contribute parameters to the same query. On the installed SQLite build, the limit is 32,766: the actual relation-query method succeeded with 32,765 member-ID parameters plus one label and failed with `too many SQL variables` when a second label was added. The direct query probe repeats a nonexistent member ID to reach the boundary; distinct selected IDs produce the same number of bindings. Failure occurs before deletion, so the transaction leaves relations unchanged and Admin shows an error.

The [old single-label lookup](https://github.com/TryGhost/Ghost/blob/5d4430c8c157990adbd69400f4cee9795037fbbb/ghost/core/server/models/member.js#L700) already had an unchunked member-ID list and failed at its own limit. The added label list moves that threshold earlier: with many requested labels, the affected range widens. SQLite is [currently supported](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/docs/codebase/direction.md#L165), although its removal is planned for Ghost 7. The later delete is already [chunked in groups of 100](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/models/base/plugins/bulk-filters.ts#L5); the preceding lookup is not. Bound both dimensions of the lookup, or use a stable-ID strategy that avoids one unbounded `IN` list, while preserving the transaction. This probe establishes an SQLite limit, not a MySQL limit.

### 2. New response type promises a field the wire response omits

The new [`BulkEditResponseType`](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin-x-framework/src/api/members.ts#L695) requires `bulk.action`. Requests are sent as [`{bulk: {action, meta}}`](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin-x-framework/src/api/members.ts#L736), and [`Frame.configure`](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/packages/api-framework/src/frame.ts#L79) keeps that nesting. The existing [output serializer](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/api/endpoints/utils/serializers/output/members.js#L63) reads `frame.data.action`, so JSON serialization omits `bulk.action`. The isolated probe used the actual frame and serializer and confirmed the omission. The changed [acceptance fixture](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin/src/members/members-bulk-actions.acceptance.test.tsx#L14) supplies the missing field, and the added [HTTP assertions](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/test/e2e-api/admin/members.test.js#L4681) check stats but not action.

The [same serializer expression existed at the baseline](https://github.com/TryGhost/Ghost/blob/5d4430c8c157990adbd69400f4cee9795037fbbb/ghost/core/server/api/endpoints/utils/serializers/output/members.js#L63). The current remove-label handler reads stats, not action, so this is not evidence that the primary UI flow fails today. It is an incorrect newly asserted API type and a trap for future callers or strict response parsing. Reconcile the type and server response deliberately, including compatibility with older servers that omit action; a schema that simply requires the newly declared field would turn successful committed edits into client errors.

### 3. The declared endpoint action allowlist is not the active validation boundary

The endpoint lists `removeLabels` in its [`validation.data.action.values`](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/api/endpoints/members.js#L344). For this custom `bulkEdit` method, the [shared validator dispatch](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/packages/api-framework/src/validators/handle.ts#L49) has no `bulkEdit` method, and the [common `all` validator](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/packages/api-framework/src/validators/input/all.ts#L117) validates options, not the nested action. The probe confirmed that the real shared validator accepts an unsupported nested action. The repository's separate [action allowlist and payload checks](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/services/members/members-api/repositories/member-repository.js#L1229) still reject unsupported actions and malformed `removeLabels` lists before any mutation. Thus this is an inherited boundary/design issue, not evidence of unauthorized deletion or a new validation bypass.

The mixed-rollout [acceptance fake](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin/src/members/members-bulk-actions.acceptance.test.tsx#L32) returns a simulated 422 `ValidationError`; it demonstrates the UI's generic rejection path, not the exact response of every older backend. Add a real API-boundary test if the declared validation behavior or status is relied upon.

## Transaction, rollout, and side-effect analysis

- [Filtered collection queries](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/models/base/plugins/filtered-collection.js#L39) apply the supplied transaction; the relation query and [bulk delete](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/models/base/plugins/bulk-operations.js#L166) do too. `throwErrors: true` rethrows a failed chunk, letting the newly created transaction roll back. A caller-supplied transaction remains under its caller's commit/rollback control. The single snapshot is taken when the request executes, not when the modal opened; no claim is made about serializing other concurrent edits.
- Core advertises the [capability](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/api/endpoints/utils/public-config/config.js#L55) and the config serializer exposes it. Admin enables multi-selection only for [strictly `true`](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin/src/members/members.tsx#L405); absent/false falls back to one label and the legacy action. A stale true capability routed to older Core sends one unsupported request, and the handler catches rejection rather than retrying partial single-label edits. These rollout claims are source analysis and mocked tests, not a real mixed-version deployment test.
- A normal member-label relationship edit emits [detach events](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/models/member.js#L553). Both the [legacy bulk path](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/services/members/members-api/repositories/member-repository.js#L1308) and the new path use raw `members_labels` deletion and do not run those model hooks or a `member.edited` model update. The [webhook listener](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/services/webhooks/listen.js#L30) listens for `member.edited`; this missing hook behavior is inherited, not a demonstrated regression caused by batching.
- The mutation [invalidates member queries](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin-x-framework/src/api/members.ts#L749), not the separate label-query key; the server bulk endpoint also retains `cacheInvalidate: false`. Label member counts can be requested through [`include=count.members`](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/ghost/core/server/api/endpoints/labels.js#L11). This cache pattern predates the PR; no affected current Admin count consumer was established.
- Beyond the demonstrated SQLite limit, scale risk remains unmeasured: the new path materializes every selected member ID and every matching relation ID at once, then holds a transaction across sequential 100-ID deletes. The old flow also materialized IDs and had an unbounded lookup, but processed one label per request and did not hold all multi-label deletions in one transaction. Lock duration, memory, timeouts and MySQL packet limits depend on workload and deployment; no production threshold was tested.

## Documentation and tests

No changed documentation specifies the new bulk request or capability. The [API design guide](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/docs/practices/api-design.md#L85) mentions `/members/bulk` generically. Useful contract details to document are the `removeLabels` body, the capability/fallback, selection-at-request semantics, transaction behavior, and that `stats.successful` counts preselected relation IDs, not distinct members (the added test expects four for two members with two labels each). The helper reports the input-ID count rather than affected rows, which can differ under concurrent changes. Nonexistent or duplicate IDs do not imply one success per requested label; describe their intended contract if external clients will use the action.

The new [fallback copy](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin/src/members/components/bulk-action-modals/remove-label-modal.tsx#L114) is a raw English JSX string, while the [Admin README](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/apps/admin/README.md#L109) directs product copy to the `ghost` namespace and the [internationalization guide](https://github.com/TryGhost/Ghost/blob/779635571ba48999068a61ae56ec1ae98678509e/docs/practices/internationalization.md#L29). Nearby pre-existing copy is also raw; supported-locale impact was not tested, so confirm the intended Admin translation workflow rather than assuming a functional localization regression.

The PR adds meaningful cases for filtered multi-removal, search/no matches, invalid payloads, rollback, feature detection and unsuccessful responses. The repository unit test uses mocks and verifies wiring; the rollback HTTP test stubs the delete rather than exercising a real later chunk. The focused probe below covers actual chunk failure under SQLite, but uses a small SQL stand-in for NQL and does not execute HTTP, the full Ghost model filter, or React. Duplicate/nonexistent IDs, combined filter plus search, large selections on MySQL, real mixed-version transport, model-event expectations and an actual response-envelope assertion remain coverage opportunities.
