## Assessment

The intended change is appropriate for an ordinary inline settings editor: a save is associated with a form version, and `useSettingGroup` only ends editing when the save returns true. One passing probe confirms that, in the tested editing scenario, head keeps B and the editor open with `unsaved` state while the base returns success and ends editing. However, the version check is shared by more than 20 direct `useForm` consumers, and the other probes expose cases where an ignored return value or API-response synchronization can bypass that protection. Browser and backend integration still require validation before accepting the PR's broad claim that newer edits remain safe.

### 1. An overlapping Save is rejected while a caller-shaped callback proceeds

**Confirmed with the real group hook and a callback-shaped test double; actual modal behavior remains untested.** At [use-form.ts:100](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin-x-framework/src/hooks/use-form.ts#L100-L103), a second call returns `false` while the first remains pending. An input event runs [updateForm](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin-x-framework/src/hooks/use-form.ts#L150-L154), which makes `saveState` `unsaved` even though that request is still outstanding. [NavigationModal](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/site/navigation-modal.tsx#L84-L102) disables its buttons only when the state is `saving`, then unconditionally calls `updateRoute` after awaiting `handleSave`. [Stripe Direct](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/membership/stripe/stripe-connect-modal.tsx#L313-L325) similarly ignores the boolean and closes; its button uses the same `saving` predicate at [line 359](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/membership/stripe/stripe-connect-modal.tsx#L359-L364). The [SettingsModal keyboard shortcut](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/shade/src/components/patterns/settings-modal.tsx#L188-L197) invokes `onOk` independently of the disabled-button prop. The settings [navigation guard blocks only history POPs](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/layout/dirty-navigation-guard.tsx#L9-L23), whereas the modal's `updateRoute` normally calls `navigate`.

The probe submits A, changes the hook state to B, and invokes a test callback that awaits `handleSave` and then marks the modal closed. On head it marks closed before A is released, only A reaches the mock API, and the mock's final persisted value is A. At the [base](https://github.com/TryGhost/Ghost/blob/80b4c5d8f8a7cb90a93caa072140c54d4cb5b69b/apps/admin-x-framework/src/hooks/use-form.ts#L98-L125), both A and B reach the mock API; the tested completion order A then B leaves the mock value B. This confirms the new rejected-second-request behavior in the probe. The base already had separate close/order races and did not reliably protect B, so the broader data-loss risk is not new. Actual component rendering, keyboard behavior, routing, and other network completion orders need integration tests.

### 2. A Design response replaces the newer edit before the version check

**Confirmed with the extracted real Design hook and a simulated response; actual UI and API remain untested.** `formVersion` is incremented by `updateForm` and `reset`, but not by the exposed [setFormState](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin-x-framework/src/hooks/use-form.ts#L131-L153). The hook checks the version only *after* awaiting `onSave`. In the actual [Design form](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/site/design-and-branding/use-design-form.ts#L43-L55), `onSave` replaces the settings array with the response; [user details](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/general/user-detail-modal.tsx#L177-L187) replaces the complete user with the response. Portal similarly uses snapshots inside response setters at [portal-modal.tsx:170](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/membership/portal/portal-modal.tsx#L170-L187); those other components were not tested.

The probe submits A, edits the same field to B, then resolves the mock API with A and no local `dirty` flags. On head, the extracted Design hook shows A, returns `false`, and remains `unsaved`; a retry returns `true` without a second mock API call. The base also shows A and makes no second call in that scenario, but returns `true` and becomes `saved` after the first completion. The overwrite therefore predates the PR; the probe confirms the proposed version guard does not itself prevent it. Separately, [Add Recommendation](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/growth/recommendations/add-recommendation-modal.tsx#L75-L115) calls `updateForm` *inside* `onSave`, which now changes the version even without a concurrent user edit. This changes the returned boolean; a harmful visible result was not established.

### 3. A context refresh overwrites dirty group state when `isEditing` is false

**Confirmed with the real group hook and simulated context; actual modal and query cache remain untested.** The [settings synchronization effect](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/hooks/use-setting-group.tsx#L85-L90) replaces local settings whenever `isEditing` is false. NavigationModal never calls `handleEditingChange`, and neither do [Code Injection](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/advanced/code/code-modal.tsx#L15-L41), [Announcement](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/site/announcement-bar-modal.tsx#L140-L145), or Slack's modal. The probe starts A, edits B without setting `isEditing`, and refreshes context with A; the actual group hook replaces B with A on both revisions. Head then returns `false`, while the base returns `true`. The same `!isEditing` branch was present at the [base](https://github.com/TryGhost/Ghost/blob/80b4c5d8f8a7cb90a93caa072140c54d4cb5b69b/apps/admin/src/settings/hooks/use-setting-group.tsx#L85-L90): the overwrite is a remaining limitation, not a newly introduced condition.

## Fairness of the received review

The only submitted review in the supplied snapshot is [CodeRabbit's review of this head](https://github.com/TryGhost/Ghost/pull/32433#pullrequestreview-5728412341); there are no inline review comments in that snapshot. Its separate [summary comment](https://github.com/TryGhost/Ghost/pull/32433#issuecomment-6550206659) describes both navigation concerns. Both point to real code paths: NavigationModal ignores the boolean, and its `isEditing` flag is never set. Treat the specific user-visible scenarios as candidates until tested, and distinguish the new overlapping-save rejection from the pre-existing unconditional close and context-refresh behavior.

The suggested guard against synchronization in `saving` and `unsaved` is not evidently sufficient for every `useSettingGroup` consumer: validation can set [`saveState` to `error`](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin-x-framework/src/hooks/use-form.ts#L105-L107) while a local setting remains dirty. For example, [Slack's modal validates without setting `isEditing`](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin/src/settings/advanced/integrations/slack-modal.tsx#L22-L38). A complete fix should define the editor lifetime and dirty/error/reset behavior, then test it; adopting the suggested two-state check without those cases may leave another overwrite path.

## Contract, tests, and documentation

- The PR's [hook documentation](https://github.com/TryGhost/Ghost/blob/2a62cbb7447c2c52e6b2be4029803f6ee64002d9/apps/admin-x-framework/src/hooks/use-form.ts#L28-L32) states when `false` is returned. It should also make clear that a stale `false` can follow a successful server write of the *earlier* snapshot, a pending-call `false` submits nothing, and thrown failures remain different from either result. Consumers that dismiss dialogs, show success, test an integration, or issue secondary actions must decide what `false` means. The PR description's statement that callers keep the editor open is broader than the audited callers support.

- The PR body reports 28 focused tests and clearly says full `pnpm check` did not complete. Those are author-reported results, not tests independently confirmed by this audit. Suggested validation includes real component/route tests with deferred API responses, same-field and different-field edits, a second Save and shortcut during a pending save, failed validation, `reset`/cancel and reopen, plus query-cache response synchronization. Record the backend state as well as the visible state and save result.
